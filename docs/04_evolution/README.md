## 4. 維護規則

1. **append，不覆蓋**：新的一條加在尾，編號接落去（A10、B8…）；舊條目唔改，
   除非發現**事實錯**（那就改並在 commit message 講清楚）。
2. 每條要有六件事：**日期／commit／改了什麼／之前→之後／量測點／正確性閘門**。
   冇數字就標「未量」，唔好寫「應該快咗」。
3. **失敗的實驗一樣要寫**（放負結果表）：寫「假設 → 實測 → 為什麼錯」。
   呢啲係最貴的資產——唔寫，下一次會再試一次。
4. **量測點要標**：`0xF062`（bench）／`0xF077`（EffectPerf）／production `enc_us`／
   host x86／邊塊板，**唔可以跨表比**。跨 IDF 版本都唔可以（AGENTS 鐵律 12）。
5. 有**物理上限**就寫達標率（UART 98%、SD 92%、16×600 線路 18 ms），
   唔好只寫「快咗幾倍」。
6. 現況數字**唔好抄進來**；留 link 去 `status.md`，避免兩邊唔同版本。

## 5. 新增一條主線（或一個子系統）時

1. 先問：它是**新主線**（入 `tech-evolution.md` 加一節）還是**獨立到值得一份文件**
   （例如 pixel 這種有 5 個階段＋失敗實驗的）？
2. 獨立文件用這個骨架：

```markdown
# <子系統> 技術進化日誌

> 為什麼有這份 / 範圍 / 唔包什麼 / 最後更新

## 0. 名詞（容易誤會的）
## 1. 一覽（表：日期｜commit｜改動｜之前→之後｜量測點）
## 2. 逐條（每條：做法 → 數字 → 為什麼有效／失敗）
## 3. 負結果
## 4. 界線／未驗證
## 5. 維護規則
## 6. Commit 索引
```

3. 加入本 README §2 的索引表，並在 `tech-evolution.md` 的主線總覽加一行指向它。
4. 更新 `AGENTS.md` §3 目錄地圖／找東西次序（只改必要的指標，唔好貼數字）。

## 6. 同其他層的邊界（避免兩套講法）

- `status.md`：**快照**，舊數字直接覆蓋；權威最高（只低於程式碼＋實測）。
- `03_notes/`：**設計理由**，描述現況機制；會隨架構改寫。
- `04_evolution/`（本層）：**歷史**，只加不改；用來回答「點解」同「試過咩」。
- 如果三邊出現矛盾：先信程式碼＋最新實測，再信 `status`，`04` 只作導航。
