# NC4 幀格式與協議參數

> **用途**：一張表講完「一幀長什麼樣、每個數字從哪裡來、哪些可以改」。
> **權威來源**：上游 `mp_Net-Core/slave/lib/sys/proto.py`（`SOF` / `CUR_VER` / `MAX_PAYLOAD` /
> `HDR_LEN` / `CRC_LEN` / `RX_BUF_SIZE` / `SEND_CAP`）。本檔只是把它寫成人看的樣子，
> **數值一律以上游為準**；兩邊改了要同步。
> 相關：[commands.md](commands.md)（有哪些指令）、[transports.md](transports.md)（通道要做什麼）

---

## 1. 幀格式（唯一權威寫法）

```text
┌──────┬───────┬────────┬───────┬───────┬──────────────┬─────────────┐
│ SOF  │  VER  │  ADDR  │  CMD  │  LEN  │     DATA     │    CRC32    │
│ (2B) │ (1B)  │  (2B)  │ (2B)  │ (2B)  │   (LEN B)    │     (4B)    │
└──────┴───────┴────────┴───────┴───────┴──────────────┴─────────────┘
  "NC"    4     0xFFFF   cmd     資料長度    指令參數/回覆        校驗
                =廣播            不含表頭    內容
```

- **`LEN` 是 `DATA` 的長度**，不含表頭、不含 CRC。
- 表頭固定 9 B：`HDR_LEN = 2 + 1 + 2 + 2 + 2`。
- 一幀總長 = `9 + LEN + 4`。
- 所有多位元組欄位一律 **little-endian**（上游 `struct.pack_into("<2sBHHH", …)`）。

### 欄位表

| 欄位 | 長度 | 值 | 說明 |
|---|---|---|---|
| `SOF` | 2 B | `"NC"`（`0x4E 0x43`） | 幀頭，用來重新同步 |
| `VER` | 1 B | `4` | 協議版本，**在 CRC 範圍內** |
| `ADDR` | 2 B | `0xFFFF` = 廣播 | 目標節點位址 |
| `CMD` | 2 B | 見 [commands.md](commands.md) | 指令碼 |
| `LEN` | 2 B | 0 – 65535 | `DATA` 位元組數 |
| `DATA` | `LEN` B | 指令參數 / 回覆內容 | 欄位順序與型別照上游 `slave/schema/*.json` |
| `CRC32` | 4 B | — | 見 §2 |

## 2. CRC32

- 演算法：標準 CRC-32（zlib / ISO-HDLC）。上游 `binascii.crc32`，固件 `esp_rom_crc32_le`，
  兩者多項式相同，輸出要位元組完全相同。
- 初始值 `0`，小端寫入。
- **覆蓋範圍 = `VER` 開始到 `DATA` 結束**（`buf[2 : 9+LEN]`）。
  **不含 `SOF`** —— 所以 `NC` 這兩個 byte 不在校驗內。

```text
        ┌── 不計 ──┐┌──────────── 計入 CRC ────────────┐
        │  SOF     ││ VER │ ADDR │ CMD │ LEN │  DATA   │
        └──────────┘└─────────────────────────────────┘
```

- 驗證失敗時**不回應、不報錯**，parser 前移 1 byte 重新找 `SOF`（靜默重同步）。
  → 已知缺口：CRC 錯誤沒有計數器，見 [decode-routes.md](../03_notes/decode-routes.md)。

## 3. 三個容易搞混的數字

這三個數字**互相獨立**，不要互相推導：

| 常數 | 值 | 管什麼 | 出處 |
|---|---|---|---|
| `MAX_PAYLOAD` | **8192** | 單幀 `DATA` 的上限；parser 緩衝 = `8192 + 13 = 8205` | 上游 `proto.py` |
| `RX_BUF_SIZE` | **4115** | 傳輸層**每個接收插槽**的大小（剛好一幀：`9 + 2 + 4 + 4096 + 4`） | 上游 `proto.py` |
| `SEND_CAP` | **4096** | 每次 `send()` 的分段上限（lwIP `TCP_SND_BUF` 約 4–5.7 KB） | 上游 `proto.py` |

- `RX_BUF_SIZE` 取「剛好一幀」不是越大越好：**扛延遲靠多插槽，不靠單槽變大**。
- `SEND_CAP` 超過 4 KB 會撞上「8 KB 懸崖」（單次 send 阻塞等 ACK），所以 4 KB 是發送端甜蜜點。

---

## 4. `8192` 到底是什麼

**不是協議規定，是一個經驗參數（magic number）。**

- 協議**本身**的上限由 `LEN` 欄位決定：2 B → 65535。
- `8192` 是上游在實測之後揀的「甜蜜點再加少少」——留一點出界餘量給使用者，
  不是因為協議只准 8192，也不是因為記憶體只夠 8192。
- 它的作用仍然是**上限**（parser 緩衝照它配），但它的**來源是經驗，不是規格**。
  所以：**改它是允許的**，改了要同步三處 —— 上游 `MAX_PAYLOAD`、固件 `NC4_MAX_PAYLOAD`
  （`firmware/components/sys/nc4/include/nc4.h`）、以及每一條 bus 實際配的 `max_frame`。

> 一句話：`LEN` 講的是「這幀有多長」，`8192` 講的是「我們允許它多長」。
> 前者是協議，後者是經驗。

## 5. 術語：不要把三個東西都叫 payload

| 講法 | 指什麼 | 在哪 |
|---|---|---|
| **`DATA`** | 幀裡 `LEN` 之後、`CRC32` 之前的那段位元組 | 協議欄位（本檔 §1） |
| **協議 payload** | 上游 code 對 `DATA` 的稱呼（`proto.py` 的 `payload` 參數） | 只在引用上游程式碼時用 |
| **回覆緩衝** | 固件裡組回覆 JSON 用的暫存區（`main.c` 的 `static uint8_t payload[2102]`） | **不是協議的一部分**，是實作細節 |

**不要**把第三個叫 payload。它是暫存，跟協議無關；而且它是「每個執行者要有一份」的東西，
不是全域一份（見 [decode-routes.md](../03_notes/decode-routes.md) §2.6）。

**也不要**把 `LEN` 寫成 `plen`。上游的字眼是 `len`（`struct.pack_into("<2sBHHH", …)`），
本檔統一寫 `LEN`。固件程式碼裡這個值叫 `dlen`（DATA 長度），因為 `len` 已經被
「緩衝區總長」用掉了 —— 但**不要**再叫它 `plen`。

## 6. 一條指令的完整組成

```text
CMD（2 B，語義所屬的域）
 └─ DATA 的欄位：名稱 / 型別 / 順序 / 預設值   ← 權威表：上游 slave/schema/*.json
```

- **指令碼**決定「做什麼」，**schema** 決定「參數怎麼排」。兩者都照上游，不要自己發明。
- 新增指令的規則見 [commands.md](commands.md) §1（四條規則）。
- 測試指令一律 `0xFxxx`，整個區段都是假的，可以隨時刪。
