Pixel 四層：緩衝、交接與流向

四層同時跑：effect 一路算、paint 一路交環格、encode 一路搬去 DMA、render 一路送。 緩衝之間有兩層箭嘴：淡淡嘅骨架標出整體流向（0 copy／1 copy）， 粗嘅一筆係具體交接 —— 由邊塊卡指去邊塊卡（例如 pool B → slot 2、slot 2 → DMA 1）。 任務與緩衝之間只畫讀寫關係（W／R）。 owner＝建立／擁有 lifetime。
一格 tick = 一個 frame_interval（20 ms 或 5 ms）。每個 tick 內部拆成有序微步： reclaim → submit → encode 讀環格 → encode 寫 DMA → paint 逐格交 → effect。「⏭ 單步」= 行一個微步， 所以 paint 交 4 格會分 4 步見到、encode 亦分兩步（先 peek 再寫 DMA）。 每個 buffer 都照實作輪替：effect pool A／B 交替、DMA 槽 round-robin、ready queue 係環（讀寫指標一路向前）。

ready queue 到底做咩？

問題：寫 DMA 槽嘅係 pixel_encode_task，叫硬件送嘅係 render_task。兩個係唔同任務（唔同優先級、唔同核心），唔可以你 call 我我 call 你。

所以：encode 寫完槽 k，只係 push 一項 {lane, slot=k, seq} 落 queue；render 的 push loop 每輪 pop 一項，再 submit(k)。

三件事：① 跨任務交棒（FreeRTOS queue，唔使自己寫鎖）；② 保證 submit 次序 = encode 次序； ③ 滿 16 項就 fallback 直接 submit（唔會漏咗個槽，令 DMA 槽永遠洩漏）。

點解成日見唔到佢有貨：單 lane 時 encode 每 tick 出 1 項、push loop 每輪就收 1 項，所以通常只有 0–1 項。 16 深係 NC_PX_MAX_LANES × 2（8 lane × 2），唔係因為單 lane 需要咁多。

DMA 槽：係緩衝，唔係頻道

佢係記憶體：每槽 = 一幀的線材格式（internal RAM，DMA-capable），由 nc_i80_drv_install() 一次過開 slot_bytes × slots。

只有一條 DMA：整條 I80（LCD_CAM）得一條匯流排，三個槽只係三緩衝（NC_I80_DRV_SLOTS_MAX = 3）， 一個送緊、一個編好等送、一個空——咁 CPU 就唔使等 DMA 送完才開始編下一幀。唔係用咗三條頻道。

箭嘴係單向：把資料由槽送去硬件；送完之後嗰個槽變成 FREE 係狀態變化 （reclaim），唔係資料回傳，所以圖上冇回程箭嘴，卡上會閃「✓ 還格」。

「綁定 slot 0」係咩：encode 揀一個空槽 k，會記低 d->seq[k] = seq、d->pay[k] = 環 payload， 即係「呢個槽而家屬於邊一格畫面」。圖上「slot 2 · DMA 2 已佔用」就係呢個對應； DMA 送完 reclaim 見到 slot_done(k) 才清 seq[k]，個槽才變返 FREE。

任務之間點耦合？邊個綁定邊個？

原則：四條任務各自係獨立 FreeRTOS task（effect core0、paint core1、encode／render core1）， 唔會互相 call function、唔會直接改對方嘅變數；大家只係睇 buffer 的狀態 （state／seq／wr）同 queue 決定做唔做嘢。

純靠緩衝：paint→環（begin 拿 FREE、commit 標 READY）、encode→環（peek 最新）、 encode→queue（push 索引）、render→queue（pop）、render→DMA（submit）、 reclaim→環（slot_done 之後才 release）。 呢幾段冇「指定對方」——任何生產者都可以餵任何一條環。

但有三個例外要知： ① 節拍：esp_timer 喺 render，encode 等它個 semaphore（nc_render_encode_wait）—— render 停，encode 就跟住停； ② ack：paint 寫 s_ack、effect 讀（volatile，無鎖），1:1 綁住兩塊 pool； ③ 環的擁有者：paint 預設只餵 nc_render_first_ring()，多後端（i80＋LCD）時第二條環冇畫面（pixel-ring-flow.md §4.5）。

所以：buffer 係唯一的資料通道（零拷貝），但「邊個叫醒邊個」仍然靠上面三個 sync 物件。 圖上每一支箭嘴都係「讀／寫某個 buffer」，冇一支係「任務 call 任務」。

環的狀態機：FREE → FILLING →（commit）READY →（peek 最新）encode →（DMA 完成）release → FREE。 FILLING 只存在 begin() 與 commit() 之間（同一個 tick 內），所以圖上唔會停喺呢個狀態。 環的 struct 只有三個 state；圖上「DMA 用緊」係畫面上嘅標記 —— 事實上嗰格仍然係 READY，要等 release(seq) 才變 FREE。
環格 ↔ DMA 槽的對應唔係綁死：穩態（paint／encode／DMA 每個 tick 各推進一格）時會見到固定配對 （ring 2 → DMA 2），純粹因為三者同步；一有抖動就會漂。切去「2,400 px · 4 子幀」跑幾步就會見到 ring 3 → DMA 0、ring 2 → DMA 1、ring 1 → DMA 2 咁跳 —— 三個環格、三個槽都一直在用，只係相位變咗。
4 子幀會漏格（現況，未修）：paint 每個視覺幀連續 commit 4 格（for sf in 0..ns）， 但 encode 每個 tick 只 peek 最新一格，並把其餘 READY 格直接釋放（假消費）。 所以 4 個子幀入面只有最後一個真的送去 DMA，另外 3 個消失 —— 睇上面「假消費」的計數。 呢個就係 pixel-ring-flow.md §4.2 講的張力（原本以為「下一個 tick 才補」，但 peek 會先把它們釋放）。
