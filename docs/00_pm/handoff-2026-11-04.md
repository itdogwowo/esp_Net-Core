## 3. 這輪定案的原則

1. **通道存在與否由 config 決定，開機只讀一次。**
   `links[].enable`（缺省 = 1，向後兼容）→ 決定宣告（plan）、bus、路由、UDP。
   要中途開啟 → 改 config ＋ 重啟；plan 的宣告窗口在 commit 之後關閉，runtime 沒有路徑。
2. **兩道閘，兩層成本。**
   編譯期決定「靜態 ＋ flash」；執行期決定「heap」。
3. **位置由用途決定。**
   每幀／每包要讀的（parser、TCP slots、decoder 表）留 internal；
   冷資料、大塊、字串（config 快照、manifest、WS/UDP 暫存）去 PSRAM。
4. **狀態管理器（ConfigManager → 狀態管理器）只定案、未實作。**
   三層（熱／冷／封存）、fast 區純數字、字典放 rodata＋PSRAM、
   `keys` 解析鏈（builtin → fast → provider → config）。**這輪沒有落 code。**

## 6. 判斷：緩衝還有沒有優化空間？

**有，但唔係「緩衝設計」問題，而係「未用的功能仍然要付費」。**

- 已經做對的：單一 heap、plan／pool／arena、零複製路徑有量測、靜態清乾淨。
- 仍然明顯浪費的：**測試 task 30.7 KB**（純 win）、**P4 tinyusb 21.7 KB**、`s_slots` ~3 KB。
  三項加起來 **~55 KB**，都係「刪／關」而不是「重新設計」。
- 之後 ROI 會急速下降：再省就要動熱路徑（搬 PSRAM 換吞吐）、縮 lwIP 緩衝（換吞吐）、
  或 per-core decoder（更多 stack）。呢啲都係**取捨**，唔係免費。

**結論**：緩衝層已經接近這個架構的上限，唔係一廂情願。
做完 P0 ＋ P1（30.7 KB／21.7 KB）就可以停手，把時間放去功能（Wi-Fi、檔案通道、fx）。
下次再檢視記憶體，應該是「要加一個大功能」的時候，而不是繼續微調。

## 8. 設計共識（本輪討論，**未實作**）

> 這一節全部是「已經講定、但一行 code 都未寫」。不要當成現況，
> 也不要重新發明 —— 下一位接手的人應該照這裡的結論往下走。

### 8.1 三層狀態

| 層 | 媒體 | 寫入政策 | 誰寫 |
|---|---|---|---|
| **熱 hot** | 內部 SRAM | 每幀／每包，原地覆寫 | 任務直接寫 slot |
| **冷 cold** | PSRAM | 少、交副本、寫入後不可變 | 任務 `put()` 交副本 |
| **封存 sealed** | flash（JSON／NVS） | 明確 `seal()`、原子、節流 | 只有狀態管理器 |

合法的跨層通道只有兩條：開機 `sealed → cold/hot`；封存 `hot/cold → sealed`。

### 8.2 兩條車道

- **高速只准整數**：`u8/u16/u32/i32/bool`、固定 slot、執行期冇名字（enum index）。
  禁止：指標、字串、malloc、cJSON、ESP_LOG、互斥鎖、阻塞呼叫。
  每個 slot 唯一寫者；多讀者用 atomic；放內部 SRAM、cache line 對齊。
- **低速**：字串／JSON／manifest／log，放 PSRAM，只在任務 context 改。
- 只有兩個轉換點：開機 `config → fast`；持久化 `fast → JSON → 原子寫檔`。

### 8.3 狀態管理器（房東，未實作）

- **角色**：房東（cfg／nc4／fx）擁有並 provide；租戶只申請；
  `nc_task`／`nc_buf` 是管理器（只配置、記帳，不擁有資料）。
- **ConfigManager 的雙重身份**：它是緩衝管理器的用戶（自己的三塊也要宣告），
  同時自己是房東（提供 `cfg.*`）。config 檔案只是它的其中一個 backend。
- **參數與數值分開**：字典條目（name／type／unit／group／backend）放 rodata＋PSRAM；
  數值放 SRAM 的 fast 區。
- **查詢鏈**：`builtin → fast slot → provider（getter）→ config path`。
- **目錄**：`keys="?"` 動態生成（builtin＋fast＋provider＋config）。
  上游**沒有** STAT_LIST／STAT_GET；不要新增指令號 —— `0x1101 keys` 已經夠。
- **合成**：bounded writer，只在成員邊界停；放不下就 `more/next` 分頁；
  `keys=""` 只回 cheap，`keys="all"` 才全部。
- **上游對照**：`bus.shared`（config 樹）、`bus._providers`（name→getter）、
  `log_service` 的 slot（name→buf/offset，純數字）、`buffer_hub.alloc_dma`（唯一 heap 入口）。

### 8.4 緩衝管理原則

- **一個入口**：plan／pool／arena 都由同一個管理器發；熱路徑不准 runtime malloc/free。
- **位置由用途決定**，不是由申請者偏好：
  1. 有硬約束？（ISR／DMA／stack／flash 操作期間／跨核鎖）→ 內部 SRAM，不討論。
  2. 每一 byte 或每一幀都要摸？→ 先量，再決定（P4 的 PSRAM 夠快，S3 較保守）。
  3. 其餘 → PSRAM。
- **PSRAM DMA 不是「不行」**：S3／P4 都有 `SOC_PSRAM_DMA_CAPABLE`，但有條件 ——
  descriptor 必須在 internal、buffer 要 cache line 對齊、前後要 msync、
  **flash 寫入期間 PSRAM 完全不可用**。`MALLOC_CAP_DMA` 不含 PSRAM。
- **跨核共享的可變狀態**留 internal ＋ 同步；不要在 PSRAM 無鎖共享。
- 靜態塊要嘛搬進 plan，要嘛 `nc_buf_adopt()` 納管（只為可見性，不搬）。

### 8.5 任務宣告（未實作）

由 `{name, bytes, cls, align}` 升級為 `{kind（用途）, loc, flags, count, elem}`：

- `kind`：FAST／SLOW／RX／TX／DMA／ARENA／POOL。
- 管理器檢查 `kind × loc` 合法性（FAST 只能 internal、DMA 只能 internal……）。
- FAST 回的是 **slot index**（不是 pointer）；POOL 兩段式；ARENA 整塊 reset。
- 不限制申請數量與類型混合；表大小才是上限（`NC_TASK_MEM_MAX`）。

## 10. 執行模型的取捨（同日追加）

舊專案（MicroPython）是 **B：每核一個合作式大循環**；C 版是 **A：每 loop 一條 FreeRTOS task**。
「FreeRTOS 是否必然更好」的完整判斷、以及「用 `group` 欄位小改裝兼容兩邊」的設計、
五個邊界條件、實作清單與驗收，全部在
[execution-model.md](../03_notes/execution-model.md)。

一句話：**A 留給會阻塞的 I/O 路徑；先做 round watchdog（~50 行）拿回 B 的卡死偵測；
低頻 loop 多起來才做 group。**
