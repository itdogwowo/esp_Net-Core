# 網絡線路效能測試（2026-11-15）

> 比較**舊 network 實作**與**新 `nc_net_lines` line 層**，並掃描 buffer 大小。
> 量測工具：`tools/net_bench.py`（NC4 STATUS 一問一答；`--burst` 先送 N 個再收）。
> 這是 request/reply 吞吐，不是單向大檔吞吐；數字會受 WiFi RSSI／host 排程影響。

## 1. 硬件

| Board | 連線 | 備註 |
|---|---|---|
| P4-ETH | ETH 10.10.1.50 | 32 MB PSRAM |
| S3-N16R8（新） | WiFi STA → AP `AX3000`，10.10.1.31 | 16 MB flash、8 MB PSRAM、RSSI 約 -75 dBm |

S3 確認：`h_ps` 約 8.1 MB、`ndec=2`；line buffer 已可在 PSRAM。
（Matrix 的 4 MB／無 PSRAM 測試是上一塊板，不再代表這塊。）

## 2. 舊 vs 新

### P4-ETH

| 模式 | 舊 driver | 新 line 層（優化 buffer） |
|---|---:|---:|
| TCP RTT p50 | **10.0 ms** | **3.5 ms** |
| TCP 1000 burst | **4,749/s** | **6,900/s** |
| UDP RTT p50 | 3.09 ms | 3.2 ms |
| WS RTT p50 | 6.63 ms | 6.6 ms |
| WS 500 burst | 719/s | **1,200/s** |
| HTTP :80 | 無 | **200 OK** |

舊 TCP 是 PULL（decode 10 ms 輪詢）；新 line 是 PUSH producer → slots → kick，
所以 RTT 由 ~10 ms 降到 ~3.5 ms。

### S3-N16R8 WiFi

| 模式 | 舊 driver | 新 line 層（優化 buffer） |
|---|---:|---:|
| TCP RTT p50 | 8.39 ms | 8.30 ms |
| TCP 500 burst | **432/s** | **985/s** |
| UDP RTT p50 | 7.60 ms | 6.88 ms |
| WS RTT p50 | 不支援 | 14–16 ms |
| WS 300 burst | 不支援 | **320–354/s** |
| HTTP :80 | 無 | **200 OK** |

舊 S3 build 的 `CONFIG_HTTPD_WS_SUPPORT` 關閉，所以舊 WS 直接沒有；新 WS 是自寫
codec，不需要這個 compile flag。

WiFi RTT 主要受 RSSI／AP 排程影響；新 driver 的優勢在 burst 吞吐（PUSH + slots）。

## 3. Buffer 掃描

### P4-ETH

| 設定 | TCP burst | WS burst | 備註 |
|---|---:|---:|---|
| TCP 2×8205 / WS 2×8192 | 6,840/s | 810/s | 最省記憶體 |
| TCP 4×8205 / WS 4×8192 | 6,821/s | 819/s | 平衡 |
| TCP 8×8205 / WS 8×24576 | 6,900/s | **1,200/s** | 目前選用；PSRAM 足夠 |
| TCP 16×8205 / WS 4×24576 | 不穩 | 1,841/s（單次） | 過大，boot/連線不穩 |

### S3-N16R8 WiFi

| 設定 | TCP 500 burst | WS 300 burst | 備註 |
|---|---:|---:|---|
| TCP 4×8205 / WS 2×8192 | ~985/s | 320–354/s | 目前選用；最穩定 |
| WS 2×24576 | ~970/s | 500 burst 不穩 | 大 slot 對小訊息沒有幫助 |
| WS 4×24576 | ~950/s | 376/s（單次） | 偶爾 timeout |
| WS 4/8×8192、8×24576 | 不穩 | timeout | 過多 slot 反而唔穩 |

## 4. 建議

- **TCP**：`4 × 8205 B` 已夠；再增加 slot 對 request/reply 沒有明顯幫助。
- **UDP**：P4 `2 × 16384 B`；S3 `2 × 8192 B`。UDP burst 本來就會掉，應看 paced 測試。
- **WS**：
  - P4 有 32 MB PSRAM：`8 × 24576 B`，換取 burst 吞吐。
  - S3 WiFi：`2 × 8192 B`，對小訊息最穩定；大 frame／batch 才考慮 24 KB slot。
- **不要盲目加大 slot 數**：S3 的 4/8 slot 測試出現 timeout；要配合 session 清理／
  接收節奏再調。
- 量測是 request/reply；下一步應加 **單向大 frame（0xF040）** 測試，才能定真正的
  MB/s 最佳 buffer。

## 5. SRAM vs PSRAM（追加）

新 config 欄位：line 的 `"mem": "auto" | "psram" | "sram"`。

- `auto`：PSRAM 優先，失敗 fallback 內部 RAM。
- `psram`：只配 PSRAM；失敗即 line 不建立（fail-visible）。
- `sram`：只配內部 RAM；slot 也放內部 RAM。

相同 buffer 大小（TCP 4×8205、UDP 2×8192、WS 2×8192）：

| Board | mem | TCP burst | WS burst | UDP 100 RTT |
|---|---|---:|---:|---:|
| P4 | PSRAM | ~6,857–7,000/s | ~1,001–1,029/s | ~3.16 ms |
| P4 | SRAM | 6,788/s | 1,024/s | ~3.20 ms |
| S3-N16R8 | PSRAM | 992/s | 364/s | ~7.23 ms |
| S3-N16R8 | SRAM | 1,021/s | 344/s | ~7.45 ms |

結論：

- 在這組小 buffer 下，**SRAM 與 PSRAM 的網絡吞吐差異在量測噪聲內**；network／WiFi 排程是瓶頸，不是 line buffer 記憶體。
- SRAM 版本需要約 65 KB 內部 RAM（TCP 32 KB＋UDP 16 KB＋WS 16 KB，另加 parser／bus），S3 仍然放得落，但再加大就會擠壓 WiFi／httpd。
- P4 的 `WS 8×24576` 大 buffer 仍建議 PSRAM；SRAM 版本沒有測到更大 slot，因為內部 RAM 成本高。
- 若要追極限吞吐，下一步應做**單向大 frame（0xF040）**，而不是 request/reply burst；request/reply 的吞吐主要受 decode／回覆路徑限制。

目前建議：

- P4：`mem=auto`（實際 PSRAM），TCP 4×8205、UDP 2×16384、WS 8×24576。
- S3-N16R8：`mem=auto`（實際 PSRAM），TCP 4×8205、UDP 2×8192、WS 2×8192。
- 若要節省 PSRAM、把 line buffer 放 SRAM：用相同小 buffer，吞吐幾乎不變，但內部 RAM 會少約 65 KB。

## 6. 最小 buffer 的 Pareto 測試（追加）

目標：**用最少 buffer 換最高速度**。固定 slot size = 8205 B（NC4 最大幀），逐條線減到 1 slot：

| Board | 設定 | TCP burst | WS burst | UDP RTT | 約用 buffer |
|---|---|---:|---:|---:|---:|
| P4 | TCP/UDP/WS 1×8205，**SRAM** | 6,825–6,969/s | 1,270–1,317/s | ~3.2 ms | ~49 KB |
| P4 | 同上，PSRAM | 6,846/s | 1,010/s | ~3.1 ms | ~49 KB |
| S3 | 同上，**SRAM** | 988/s | 320/s | ~7.4 ms | ~49 KB |
| S3 | 同上，PSRAM | 968–1,083/s | 316–372/s | ~7.6 ms | ~49 KB |

- P4 的 1-slot **SRAM** 版本反而比大 PSRAM buffer 更快（WS ~1.3k/s vs 1.2k/s），
  而且 buffer 由 ~393 KB 降到 ~49 KB。
- S3 的 1-slot PSRAM 版本與 SRAM 版本差不多；考慮內部 RAM 要留給 WiFi／httpd，
  S3 用 PSRAM。
- **S3 用 2 slots × SRAM 會把內部 RAM 吃到只剩 ~1.4 KB，WiFi 直接斷線**；
  SRAM 版只可以 1 slot／線，或要再減其他 task。

## 7. 最終建議（經濟型）

| Board | TCP | UDP | WS | mem |
|---|---|---|---|---|
| P4-ETH | 1×8205 | 1×8205 | 1×8205 | **sram** |
| S3-N16R8 | 1×8205 | 1×8205 | 1×8205 | **psram** |

- 每條線只佔 `8205 B slot + 8205 B parser ≈ 16.4 KB`，三條合計 ~49 KB。
- P4 用 SRAM 已經足夠，不需要 PSRAM。
- S3 用 PSRAM，保留內部 RAM 給 WiFi／httpd。
- 如果 WS 要 batch 多個 8K 幀，才把 WS 改成 `1×24576` 或 `2×24576`；純 STATUS／
  指令流量不需要。

## 8. 一個設定走天涯（P4 + S3 公約數）

目標：同一組 line buffer／mem 設定，P4 ETH 與 S3 WiFi 都用。

```json
TCP: 2 × 8205, UDP: 1 × 8205, WS: 2 × 8192, mem: "auto"
```

- `auto`：兩塊板都有 PSRAM，實際都會用 PSRAM；如果將來有一塊冇 PSRAM，會 fallback SRAM。
- 合計 configured buffer 約 **80 KB**（TCP 32.8 + UDP 16.4 + WS 32.8）。
- `iface`／network 仍然係板子各自的（P4 eth、S3 wifi）；「同一個設定」指 line buffer／mem profile，不是整個 system.json 完全相同。

實測（P4 10.10.1.50、S3 10.10.1.31，S3 STA AX3000）：

| Board | TCP burst | WS burst | HTTP |
|---|---:|---:|---:|
| P4 | **6,961/s**（1000） | **1,027/s**（500） | 200 |
| S3 | **950/s**（500） | **302/s**（300） | 200 |

取捨：

- P4 用 **1-slot SRAM** 可以做到 WS ~1.3k/s，但 S3 不能安全共用（2 slots SRAM 會餓死 WiFi）。
- 這組 2/1/2 + `auto` 是兩塊板都能穩定跑的公約數；P4 WS 比 SRAM 極限低約 20%，但換來同一個 profile。
- 1/1/1 的 49 KB 版本 P4 TCP 1000 burst 間中 timeout；2 個 TCP slot 比較穩。
- WS 2 slots × 8192 比 2×24576 更穩定，而且小訊息速度一樣；只有 batch 大 frame 才需要 24 KB。

## 9. 單向大 frame（0xF040 NETBENCH）與指標澄清

`net_bench.py` 的 `6,961/s` 是 **STATUS 一問一答**，每幀約 100 B，
不是 MB/s；換算只有 ~0.7 MB/s。之前講的 8–10 MB/s 是**單向大 frame**，兩者不能直接比。

用 test build 的 `0xF040 NETBENCH`（8,000 B payload、500 幀、batch=1）重測：

| Board / driver | TCP | WS | 備註 |
|---|---:|---:|---|
| P4 舊 driver | 5.42–5.59 MB/s | ~5.15 MB/s | 背景 test tasks 已停用 |
| P4 新 driver（2/1/2，PSRAM） | ~5.62 MB/s | 4.65 MB/s | 與舊 driver 接近 |
| P4 新 driver（2/1/2，SRAM） | 5.56 MB/s | 4.71 MB/s | PSRAM/SRAM 差不多 |
| P4 新 driver（1/1/1，SRAM） | **0.07 MB/s**（493/500 lost） | 4.03 MB/s | TCP 1 slot 不夠 burst |
| P4 新 driver（8 slots + 4×WS） | 3.70 MB/s（單次） | 5.02 MB/s | 大 buffer 沒有穩定提升 |

結論：

1. **8–10 MB/s 在這次乾淨 test build 沒有重現**；最高約 5.6 MB/s TCP、5.0 MB/s WS。
   如果之前有 8–10 MB/s 的 log／指令，要用同一條件再對照。
2. **WS 的 1,027/s 是細 STATUS**；單向 8K WS 約 4.6–5.0 MB/s，低於 TCP 約 10–15%，
   主要係 WS framing／copy 成本，不是「WS 只值 1 MB/s」。
3. **最少 buffer 不是 1 slot TCP**：單向 burst 會大量 lost；TCP 最少 2 slots。
   UDP 可以 1 slot；WS 2 slots 比 1 slot 好。
4. **PSRAM 不會自動令網絡中斷**。P4 PSRAM／SRAM 單向速度差不多；
   S3 之前斷線是因為 **2 slots × SRAM 把內部 RAM 食到剩 1.4 KB**，WiFi task 起不來。
   PSRAM line buffer 反而保留內部 RAM 給 WiFi／httpd。
5. 其他背景測試（`nc_test_tcp_start`、NETAUTO、ESP-NOW）已在 test build 停用；
   仍保留 test action component，所以不是「完全空白 firmware」。

公約數仍然是：

```text
TCP 2 × 8205
UDP 1 × 8205
WS  2 × 8192
mem: auto（兩塊板實際 PSRAM）
```

這是目前同時滿足「穩定 burst」與「~80 KB buffer」的最小組合。

## 10. 1K／2K／4K／8K 單向測試（追加）

用乾淨 test build（背景 test tasks 停用）量 0xF040，payload 分別 1K／2K／4K／8K；
TCP 用 batch=10，WS 用 batch=1（WS 一則訊息放多幀會超過 slot）。

### P4 TCP

| payload | 幀數 | 速度 |
|---:|---:|---:|
| 1,024 B | 4,000 | 5.42 MB/s |
| 2,048 B | 2,000 | 5.08 MB/s |
| 4,096 B | 1,000 | 5.61 MB/s |
| 8,000 B | 500 | 5.55 MB/s |

### P4 WS

| payload | 幀數 | 速度 |
|---:|---:|---:|
| 1,024 B | 2,000 | 1.87 MB/s |
| 2,048 B | 1,000 | 2.91 MB/s |
| 4,096 B | 500 | 3.90 MB/s |
| 8,000 B | 250 | 4.60 MB/s |

結論：

- **TCP 不是「包太小」**：1K–8K 都在 5.1–5.6 MB/s 平台，1K 沒有特別快。
- **WS 明顯受每則訊息固定成本影響**：1K 只有 1.87 MB/s，8K 升到 4.60 MB/s。
  所以 WS 若要高吞吐，應該加大 frame／batch；但 batch 之後的總訊息不可超過
  WS slot（目前 8192 B），否則 server 會斷線（測試曾出現 broken pipe）。
- 8–10 MB/s 仍然沒有重現；目前 P4 上限約 5.6 MB/s TCP、4.6 MB/s WS。
- UDP 1K 以上會嚴重掉包（NC4 沒重傳），不適合拿來做可靠吞吐基準。
