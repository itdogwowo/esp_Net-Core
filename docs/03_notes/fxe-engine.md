# FXE 引擎：模組化程式碼的執行載體

> **用途**：講清楚 FXE 引擎**專責做什麼**。
> **狀態**：載入／驗證／arena／attach／tick／預算都已實作；**執行引擎（WAMR）未接**，
> 所以現階段模組「登記得到、跑不到」。
> **相關**：[naming.md](naming.md) §5（術語）、[fx-loader.md](fx-loader.md)（容器格式與 manifest）、
> [fx-contract.md](fx-contract.md)（模組 ABI 與記憶體邊界）、[task-lifecycle.md](task-lifecycle.md)

---

## 0. 一句話

**FXE 引擎是一個「延後綁定」（late binding）機制：把本來會編進固件、只能靠重新燒錄才能改的功能，
變成換一個檔案就換行為的模組。**

它載入的是**模組化的可執行程式碼**；引擎只負責這段程式碼怎麼活、活多久、跑多久。

---

## 0.5 什麼時候用它、什麼時候不要

**正常情況下，功能就編在固件裡。** 引擎是給「需要後期調整、又不想整片重燒」的那一小部分用的。

| 情況 | 用引擎？ | 例子 |
|---|---|---|
| 需要後期調整、但不想整片重燒 | ✅ | **TFT 控制**（初始化序列、時序、gamma 參數）、UI 版面（LVGL）、驅動參數、效果 |
| 開機必需（沒有它板子起不來） | ❌ 留在固件 | 通道、解碼、任務管理器、檔案系統 |
| 時序敏感 / 要碰中斷 | ❌ 留在固件 | DMA、ISR、PHY 初始化、**TFT 的傳輸路徑本身**（SPI/DMA 搬像素） |
| 跟硬體版本綁死 | ❌ 留在固件 | 腳位、時鐘、快閃參數 |

> **TFT 控制要分兩半看**：**參數與初始化序列**（一堆暫存器值、時序、gamma）很適合做成模組 ——
> 面板換批次、調色、修時序都不用重燒；但**把像素送出去的傳輸路徑**（SPI/DMA、中斷）
> 必須留在固件，因為它跟時序與硬體綁死。

使用的先後順序，大致照「**改的頻率 × 重燒成本**」排：

1. **TFT 控制參數**（初始化序列、時序、gamma）—— 面板廠商改一次你就要跟一次；
2. **UI**（LVGL 版面、選單、字型配置）—— 改最多次；
3. **驅動參數**（裝置初始化序列、校正值）；
4. **效果／其他**（週期性輸出之類）。

判準很簡單：**這件事會不會在出貨之後一直改？** 會 → 適合做成模組；不會 → 編進固件。

## 1. 專責：六件事，從檔案到一段受管理的執行

| # | 專責 | 產出 | 實作 |
|---|---|---|---|
| 1 | **接管執行空間** | 一塊 arena，**只給被載入的模組**用（固件內建功能照自己的 plan 宣告，不經引擎） | `nc_fx_init(arena, bytes)` |
| 2 | **發現與載入** | 目錄裡的 `.fxe` → 模組實例 | `nc_fx_scan(dir)` / `nc_fx_load(path)` |
| 3 | **驗證**（容器 + 自我宣告） | 通過才成為模組；不通過就拒絕，不佔 slot | `verify_header()` / `parse_manifest()` |
| 4 | **配置記憶體** | 每個模組按自己宣告的 `mem_bytes` 取得一段線性記憶體 | `alloc_slot()` |
| 5 | **掛上生命週期** | 模組成為任務管理器眼中的一個租戶（可查、可停、可卸載） | `nc_task_attach()` |
| 6 | **驅動與監督** | 每個 tick 呼叫模組一次、量時間、超支記 strike、三次就停用 | `nc_fx_tick()` / `nc_fx_task()` |

再加上兩個操作：**啟用**（指定哪個模組接收 tick，`nc_fx_select`）與
**卸載**（`nc_fx_unload`，arena 回收、任務移除）。

**這六件事就是引擎的全部。** 模組內部做什麼，引擎不知道也不參與。

## 2. 它在系統裡的位置

```text
檔案系統                 FXE 引擎                        任務管理器
 .fxe  ──載入──►  驗證 → arena 切塊 → attach ──►  租戶（可停、可卸載）
                          │
                          │ 每 tick 呼叫一次
                          ▼
                    模組的進入點（backend）
```

引擎是**載體**：它把「一段外來的程式碼」變成系統裡一個**有記憶體、有生命週期、有預算、
可被隔離**的執行單位。這件事與模組的內容無關 —— 任何模組都走同一條路。

---

## 3. 行為規則（是規則，不是本質）

| 規則 | 現況 | 為什麼 |
|---|---|---|
| **一次一個 active 模組** | `s_live` 單一指標；換人時舊的兩 tick 後釋放 | 一次只監督一個最簡單；多個要處理「誰先跑、預算怎麼分」 |
| **每個 tick 呼叫一次** | 週期由模組宣告的 `fps` 決定（沒有就 10 ms） | 統一的節拍，引擎不必知道模組在裡面做什麼 |
| **時間預算 + strike** | 超過 `budget_us` 記一次；連續 3 次 → 停用 | 一段壞掉的程式碼不可以拖垮整個系統 |
| **失敗隔離** | 模組自報錯誤 → 立刻停用；驗證不過 → 拒絕載入 | 一個模組的失敗不影響其他模組與核心 |

要改的話是改規則（例如允許 N 個 active 模組），不是改引擎的定義。

---

## 4. 執行空間：arena 的大小由宣告決定

```
nc_plan_commit(avail[])            ← 每個 class 一次 carve
        │
        ▼
任務宣告的 arena（class 由宣告決定：PSRAM / INTERNAL / DMA 都可以）
        │
        ▼
FXE 引擎 init(arena, bytes) → 切成 slot（NC_FX_MAX_MODULES = 8）
        │
        ▼
每個模組按自己的 mem_bytes 再切
```

**arena 的大小是宣告值，不是引擎的上限。** 今天 `main.c` 宣告 512 KB
（`NC_FX_ARENA_MAX`）；要 2 MB、要用內部 RAM、要兩塊不同 class，都是改宣告，
`nc_plan` 只回答「夠不夠」。引擎對大小沒有意見。

**arena 只是「被載入的模組」的記憶體來源，不是全系統的記憶體通道。**
固件內建的功能照自己的 `mem[]` / `declare()` 向 plan 要，完全不經過引擎。

## 5. 生命週期

```text
   .fxe 檔
     │ 載入
     ▼
 [已載入] ── 驗證不過 ──► 丟棄（不佔 slot）
     │ 切到 arena、attach 成任務
     ▼
 [待用] ── 啟用 ──► [執行中] ── 每 tick 呼叫
     ▲                  │
     │                  ├─ 超預算 3 次 → [停用]
     └──── 停用 ────────┤
                        └─ 回報錯誤 → [停用]
     │
     └─ 卸載 → arena 回收、任務移除
```

| 術語 | 意思 |
|---|---|
| **載入 / 卸載** | 檔案 → 模組；模組 → 消失（記憶體回收） |
| **啟用 / 停用** | 哪個模組接收 tick；停止接收 tick |
| **tick** | 引擎呼叫模組的那一下（API 名稱是 `render`，語義是 tick） |
| **strike** | 一次超預算的記錄；連續 3 次就停用 |

## 6. 對外接口（引擎提供什麼）

| 給誰 | 提供什麼 |
|---|---|
| 任務管理器 | 每個模組登記成一個租戶（`nc_task_attach`）；可查、可停、可卸載 |
| plan | 一項記憶體宣告（arena）；模組的記憶體不進 plan，從 arena 切 |
| 上層（main / 指令） | `nc_fx_load` / `nc_fx_select` / `nc_fx_unload` / `nc_fx_info_json` / `nc_fx_status_json` |
| 執行引擎（backend） | 插槽 `{init, render, deinit}`；「怎麼跑」是可換的 |

## 8. 下一步計劃（未開工，先寫清楚）

「模組登記得到、跑不到」不是 bug，是**故意留的下一步**。要接上去的次序如下，
每一步都可以獨立驗收，不需要一次做完：

| 階段 | 做什麼 | 驗收方式 |
|---|---|---|
| **P1 後端介面固定** | 把 `nc_fx_backend_t {init, render, deinit}` 定義成公開合約（見 [fx-contract.md](fx-contract.md)），stub 照合約實作 | host test：載入 → tick → 卸載，stub 的 `render` 被呼叫 N 次 |
| **P2 接 WAMR** | 把 WAMR 的 `wasm_runtime_instantiate` / `_lookup_function` / `_call` 包進 backend；arena 當 WAMR 的 heap | 一個最簡單的 `.wasm` 能跑 `render()` 並回 0 |
| **P3 AOT / XIP** | `fmt == aot` 走 `wasm_runtime_load` 的 AOT 路徑。**注意 S3 是 Xtensa、P4 是 RISC-V**，AOT 映像不可共用 → 靠 `.fxe` header 已有的 `target` 欄位分流（`verify_header()` 現在就擋錯 target） | 同一支模組，S3 的 AOT 版與 wasm 版行為一致；P4 拿到 Xtensa 的 AOT 會被拒 |
| **P4 呼叫固件 API** | 模組要能叫 `nc_hub` / plan 之類；用 WAMR 的 native symbol 註冊，**白名單制**，不是全部開放 | 模組能發一幀 NC4 出去，且只能叫白名單內的函式 |
| **P5 多核** | 每個核一個引擎實例（§7 第 5 條）；先確認 P1 的狀態都收在實例裡、沒有 static | 兩核各跑一個模組，互不干擾 |

> 為什麼要分成五步：P1 之前，「接 WAMR」等於同時改介面＋改引擎＋改記憶體，
> 一旦跑不動分不清是 WAMR 的問題還是我們的介面問題。P1 做完之後，
> WAMR 只是一個「實作 backend 的人」。
>
> **在此之前，模組功能請一律編在固件裡**（見 §0.5）—— 引擎不是必需品。
