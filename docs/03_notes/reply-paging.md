# 回覆分頁（比推高上限更根本）

> 2026-11-28 用家指正：**8,211 B 冇解決「超大回覆」**，只係推高天花板；
> 真正做法係「回覆自己講仲有幾多頁」，主機再讀。記憶體我哋之前省了很多，唔怕用多少少。

## 1. 現況（未分頁）

| 機制 | 行為 | 問題 |
|---|---|---|
| `NC4_REPLY_JSON_MAX`（= payload−2） | 一份回覆最多 8,191 B | 超過就冇路走，只係天花板高咗 |
| `reply_too_big` | 回 `{"err":"reply_too_big","need":N,"cap":M}` | 主機知道爆，但**唔知點續讀** |
| `status` 的 `truncated:1` | 砌唔落就回精簡合法物件 | 同上：冇 cursor |

即係「**講咗唔夠，但冇教點讀落去**」。

## 2. 協議：只加兩個值（用家 2026-11-28 定案）

> 「協議只加一個回覆數值告訴主機有沒有下一頁；有下一頁就暫時禁止主機發送，
> 保持半雙工。然後要想超時問題 —— 所以是要加**兩個值**。」

回覆尾（`0x1102 STATUS_RSP`）加：

```json
{"sys":{…},"storage":{…},"more":1,"timeout_ms":40}
```

| 值 | 意思 |
|---|---|
| `more` | `1` = 仲有下一頁；`0`／省略 = 完 |
| `timeout_ms` | 由**這一刻**起，主機要靜默幾多 ms（半雙工窗口）；`more=0` 時可省 |

**唔加**：`--all`、`next` key 清單、`pages` 總數、`from` cursor —— 用家明確話
唔好加額外行為，跟協議。主機想知道邊啲未送，就用現有 `keys` 自己分批問。

### 2.1 半雙工規則

- 收到 `more=1` → 主機**停止發送任何幀**（包括其他指令），直到 `timeout_ms` 過去。
- 窗口內裝置仍然可以送（下一頁／其他廣播）；主機只收。
- `timeout_ms` 由裝置估：下一頁砌好要幾耐（實測 + 餘裕），要**保守**（寧長勿短）。
- 窗口過後主機可以用**原本的 keys 再問**；裝置由上次斷點續（內部記 cursor）。

### 2.2 逾時與續讀

- 主機若喺窗口內硬送 → 裝置**丟棄**該幀並回 `{"err":"busy_page"}`（唔會當新請求）。
- 主機如果等超過 `timeout_ms × 2` 都收唔到下一頁 → 當一次失敗，重新由 keys 開始。
- 裝置要保證：`timeout_ms` 內一定送完（或送完最後一頁時 `more=0`）。

### 2.3 邊個決定頁界

裝置按剩餘容量砌，砌到差唔多就停，寫 `more=1`＋`timeout_ms`。
唔可以砌完才發現爆（會切半）；所以 handler 要**先量後砌**（見 §4）。

## 3. 對記憶體的影響

分頁之後，回覆緩衝**唔需要 8,211**——保持 2,600（甚至更細）都可以，
因為「放唔落」變成「下一頁」。所以：

- 短期：8,211（已改）→ 先唔動；
- 做分頁之後：可以**回退到細緩衝**，省返 ~11 KB。

即係 8,211 係臨時天花板，分頁才係「冇天花板」。

## 4. 要改嘅位

1. `main.c` 的 `on_status_get`：砌之前檢查剩餘容量，砌唔落就停，寫 `more`／`next`
   （唔可以砌完才發現爆，因為已經切半）。
2. 每個 `status_put_*` 要能「由第 N 項開始寫」——而家全部由頭寫。
3. `nc4.c` 的 `reply_open`／pack：預留 2 個欄位空間（`more`／`next` 由 handler 自己寫尾）。
4. 主機：**唔加 `--all`**；`nc4.py status` 照舊一次過，主機自己按 `more`／`timeout_ms` 決定幾時再問。

## 5. 測試（重點）

- 單元：假 builder 砌到「差 1 B」→ 斷言回合法 JSON、`more=1`、`next` 指返未送項；
- 單元：剛好滿 → `more=0`；
- 端到端：兩頁拼埋要等於一次砌晒的輸出（逐 byte 比）；窗口內送幀要回 `busy_page`。
