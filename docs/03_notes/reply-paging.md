# 回覆分頁（比推高上限更根本）

> 2026-11-28 用家指正：**8,211 B 冇解決「超大回覆」**，只係推高天花板；
> 真正做法係「回覆自己講仲有幾多頁」，主機再讀。記憶體我哋之前省了很多，唔怕用多少少。

## 1. 現況（未分頁）

| 機制 | 行為 | 問題 |
|---|---|---|
| `NC4_REPLY_JSON_MAX`（= payload−2） | 一份回覆最多 8,191 B | 超過就冇路走，只係天花板高咗 |
| `reply_too_big` | 回 `{"err":"reply_too_big","need":N,"cap":M}` | 主機知道爆，但**唔知點續讀** |
| `status` 的 `truncated:1` | 砌唔落就回精簡合法物件 | 同上：冇 cursor |

即係「**講咗唔夠，但冇教點讀落去**」。

## 2. 分頁設計（兩層）

### 2.1 key 層（覆蓋 90%）

status 由十幾個獨立區塊組成，天然可分。回覆加：

```json
{"sys":{…},"storage":{…},"more":1,"next":"cfg,log"}
```

- `next` = 未送出的 key 清單（逗號分隔）；`more=0` 或冇 `next` = 完。
- 主機 loop：`STATUS_GET keys=<next>`，直到 `more=0`。
- 舊主機唔識 `more` → 行為不變（照舊分批問）。
- 冇 `truncated`，因為「未送」係正常狀態，唔係錯誤。

### 2.2 item 層（單一區塊本身都爆）

`tasks`／`mem`／`modules` 呢類一個 key 就可以爆。回覆加 cursor：

```json
{"tasks":[ … 12 項 … ],"more":1,"next":"tasks","from":12}
```

- `from` = 下一項 index；主機原 keys 再帶 `from`。
- 送唔完嘅項一定係完整項（唔會切半個 JSON object）。

### 2.3 共同規則

- 一頁一定係**合法完整 JSON**；`more=1` 時 `next`／`from` 必有。
- 分頁只影響「送幾多」，唔影響語義（同一個 key 的內容一樣）。
- `reply_too_big` 保留做保險（實作 bug 時最後防線），正常路徑唔應該見到。

## 3. 對記憶體的影響

分頁之後，回覆緩衝**唔需要 8,211**——保持 2,600（甚至更細）都可以，
因為「放唔落」變成「下一頁」。所以：

- 短期：8,211（已改）→ 先唔動；
- 做分頁之後：可以**回退到細緩衝**，省返 ~11 KB。

即係 8,211 係臨時天花板，分頁才係「冇天花板」。

## 4. 要改嘅位

1. `main.c` 的 `on_status_get`：砌之前檢查剩餘容量，砌唔落就停，寫 `more`／`next`
   （唔可以砌完才發現爆，因為已經切半）。
2. 每個 `status_put_*` 要能「由第 N 項開始寫」——而家全部由頭寫。
3. `nc4.c` 的 `reply_open`／pack：預留 2 個欄位空間（`more`／`next` 由 handler 自己寫尾）。
4. 主機：`tools/nc4.py status` 加 `--all`（自動 loop）；舊模式照舊一次。

## 5. 測試（重點）

- 單元：假 builder 砌到「差 1 B」→ 斷言回合法 JSON、`more=1`、`next` 指返未送項；
- 單元：剛好滿 → `more=0`；
- 端到端（host）：`--all` 由頁 0 讀到完，拼埋等於一次大 builder 的輸出（逐 byte 比）。
