# 回覆分頁（比推高上限更根本）

> 2026-11-28 用家指正：**8,211 B 冇解決「超大回覆」**，只係推高天花板；
> 真正做法係「回覆自己講仲有幾多頁」，主機再讀。記憶體我哋之前省了很多，唔怕用多少少。

## 1. 現況（未分頁）

| 機制 | 行為 | 問題 |
|---|---|---|
| `NC4_REPLY_JSON_MAX`（= payload−2） | 一份回覆最多 8,191 B | 超過就冇路走，只係天花板高咗 |
| `reply_too_big` | 回 `{"err":"reply_too_big","need":N,"cap":M}` | 主機知道爆，但**唔知點續讀** |
| `status` 的 `truncated:1` | 砌唔落就回精簡合法物件 | 同上：冇 cursor |

即係「**講咗唔夠，但冇教點讀落去**」。

## 2. 權威參考：mp_Net-Core 點做（`slave/lib/sys/signal_router.py:table()`）

舊項目的分頁**唔係** `more/next`，而係**請求驅動的頁碼**：

```json
{"page":0,"pages":3,"page_size":32,"total":95,"routes":[…]}
```

- `page_size` 只為咗守住 `MAX_PAYLOAD = 8192`（原文註釋）；唔夠就調細。
- 主機自己指定 `page` 再問；**裝置唔會主動推下一頁**。
- 冇 `timeout`、冇半雙工窗口 —— 因為係一問一答。

## 2.1 所以 C 版應該照抄呢個形狀

| 欄位 | 意思 | 來源 |
|---|---|---|
| `page` | 今次係第幾頁（0 起） | 權威 |
| `pages` | 總共幾頁（**主機睇 `page+1 < pages` 就知有冇下一頁**） | 權威 |
| `page_size`／`total` | 每頁幾多／總共幾多 | 權威 |
| `timeout_ms` | **新增**：主機靜默窗口（半雙工），權威冇 | 用家今次要求 |

即係「有冇下一頁」用 `pages` 表達（唔另開 `more`），第二個值係 `timeout_ms`。
`timeout_ms` 缺席＝舊行為；舊主機唔識就照舊逐頁問。

## 2.2 半雙工（新增部分，權威冇）

- `timeout_ms > 0` → 主機收到這一頁之後要靜默，直到窗口過。
- 窗口內主機硬送 → 丟棄＋`{"err":"busy_page"}`。
- 窗口過後主機用同一組 keys 加 `page+1` 再問。

## 2.3 頁界

裝置按剩餘容量砌，砌唔落就停（先量後砌）；最後一頁 `page+1 == pages`。
## 3. 對記憶體的影響

分頁之後，回覆緩衝**唔需要 8,211**——保持 2,600（甚至更細）都可以，
因為「放唔落」變成「下一頁」。所以：

- 短期：8,211（已改）→ 先唔動；
- 做分頁之後：可以**回退到細緩衝**，省返 ~11 KB。

即係 8,211 係臨時天花板，分頁才係「冇天花板」。

## 4. 要改嘅位

1. `main.c` 的 `on_status_get`：砌之前檢查剩餘容量，砌唔落就停，寫 `more`／`next`
   （唔可以砌完才發現爆，因為已經切半）。
2. 每個 `status_put_*` 要能「由第 N 項開始寫」——而家全部由頭寫。
3. `nc4.c` 的 `reply_open`／pack：預留 2 個欄位空間（`more`／`next` 由 handler 自己寫尾）。
4. 主機：**唔加 `--all`**；`nc4.py status` 照舊一次過，主機自己按 `more`／`timeout_ms` 決定幾時再問。

## 5. 測試（重點）

- 單元：假 builder 砌到「差 1 B」→ 斷言回合法 JSON、`more=1`、`next` 指返未送項；
- 單元：剛好滿 → `more=0`；
- 端到端：兩頁拼埋要等於一次砌晒的輸出（逐 byte 比）；窗口內送幀要回 `busy_page`。

## 6. 現況（2026-11-28 落地後）＝仲未係真分頁

用家指正：**內容本身唔應該有上限**；2,600 只可以係「一頁」的上限，過長就分頁。

而家 C 側做咗嘅：
- `0x1102 = [len][json][more][timeout_ms]`（跟 schema）；
- JSON 只有 `cap-3` 可用，砌唔落 → **回 `truncated` 合法物件、`more=1`**。

**未做（所以仲有上限）**：
1. 請求冇 `page` —— 主機想攞第 2 頁，冇辦法指名；
2. 裝置冇「由第 N 個單位開始砌」的能力 —— `status_put_*` 全部由頭寫；
3. 所以 `truncated` 之後，主機只可以**自己拆 keys**（唔係真續頁）。

要真正做到「冇上限」：
- `0x1101` payload 追加 `page(u16)`（缺席 = 0，舊主機安全）；
- 單位＝**key**（按固定次序 sort），`page × page_size` 之前的 key 直接跳過；
- 單一 key 自己都爆（`mem`／`tasks`）→ 該 block 內部再分頁（`item_page`），
  或者該 key 回 `{page,pages,total}` 由主機再問（同 mp 的 `table()` 一樣形狀）。

即係：**page 上限 ≠ 內容上限**；而家兩者仍然係同一個數，呢個就係要改嘅地方。
